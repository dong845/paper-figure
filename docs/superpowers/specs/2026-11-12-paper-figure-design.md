## 1. 意图与为什么

AI 方向的研究者给论文画示意类图（方法总览图、teaser、模块细节图）时，最花时间的是**排布**（过紧过松都不好）和**配色**，最不满意的是**质感一般**。"把框和箭头画出来"本身不难，难的是让图达到顶会水准，同时忠实于论文内容，并且可以继续编辑。

paper-figure 是一个 Claude Code skill。它读取用户的论文 draft 和/或代码，学习同领域顶会论文的画法，结合一个有出处、会不断增长的知识库，产出**可编辑的 drawio 文件和对应的 PNG**。出图前要经过自查，交付时附带修改前后的对比。

**前车之鉴** **[用户决定]**：用户以前有一个同类的 `paper-figures` skill，2026-08-01 删掉了，原因是**出图质量不行**。所以本项目的头号风险是出图质量，不是功能齐不齐：先证明质量能达标，再铺开功能和知识库（见第 14 节分期）。旧 skill 时期定下的个人画图偏好（如箭头不加文字、粉色表示训练专用路径等）**不再适用**，风格由"选质感"环节决定。

**和已有工作的差别**（调研见第 13 节）：PaperBanana、AutoFigure 只读论文文字，PaperBanana 出的还是不可编辑的位图。paper-figure 的不同在于：(a) **draft 和代码一起读、互相对账**；(b) **原生可编辑的 drawio 输出**；(c) **用户亲自选质感**；(d) **知识库每条有出处、随使用增长**。

## 2. 目标 / 非目标 / 反目标

**目标**
- G1 产出可编辑的 `.drawio` 和高分辨率 `.png`，覆盖三类图 **[用户决定]**：方法总览图（overview / pipeline）、首页 teaser 图、模块细节图。这里的 teaser 指**概念对比示意** **[用户决定]**，例如"已有方法 vs 本文方法"的并排框图，仍然以框和箭头为主，和方法图共用同一套蓝图和编译器（用 `groups` 表示并排的面板）。由真实结果拼成的展示图**不在**范围内。
- G2 覆盖各个 AI 方向 **[用户决定]**：CV、NLP/LLM、多模态、生成模型/扩散、RL、图学习、语音、机器人、3D、医学影像等。
- G3 作者给新模块起的名字（全名 + 缩写，例如 "Cross-Scale Fusion Module (CSFM)"）要原样出现在图中对应位置 **[用户决定]**。
- G4 排布疏密适中、配色得当、质感达到顶会水准。这是成败的主标准。
- G5 走线正确、主要组件齐全，并且能追溯到 draft 或代码里的出处。

**非目标**
- 数据图表（柱状图、折线图、消融可视化等 matplotlib 类的图）**[用户决定]**。
- 整篇论文的排版，以及海报、slides。
- 替用户决定方法本身该怎么设计。

**反目标**（技术上能跑通，也算失败）
- 图里出现 draft 和代码中都找不到依据的模块或连线（编造）。
- 知识库里出现没有出处的"规律"或数值，比如凭印象写的"NeurIPS 常用色"。
- 用占位图或编造的样例冒充真实素材，并且没有醒目标注就交付。
- 交付的 PNG 和 drawio 内容不一致，或者 drawio 打开后结构乱掉、无法编辑。
- 自查"全绿"，但实际看图一眼就能发现问题。必须看真实渲染出来的 PNG，不能只信检查脚本的结果。

## 3. 输入与输出

**输入**
- 论文 draft：`.tex`（可以是整个目录）、`.pdf`、`.md`、`.docx` 之一或多个。
- 代码：本地仓库路径。
- draft 和代码只有一样也能工作；**两样都有效果最好** **[用户决定]**。
- 目标会议（必填；用户不说就问）、图的类型（三类之一）、目标宽度（单栏或双栏，可从会议推断）。
- 可选：用户指定的参考论文，或"就学这篇"。

**输出** **[用户决定：drawio + PNG]**
- `<name>.drawio`：可编辑源文件。
- `<name>.png`：高分辨率位图，按目标打印宽度导出（**[我的决定]** 至少 300 dpi 等效分辨率）。
- **[我的决定]** 另外导出 `<name>.pdf`（矢量），因为 LaTeX 投稿更适合用矢量图。成本几乎为零，用户不要可以关掉。
- `blueprint.json`：蓝图，见第 5 节。
- `review/`：初稿到终稿的并排对比图和修改清单。
- 输出目录 **[留给实现者]**：默认放在用户 draft 旁边的 `figures/paper-figure/<name>/`，可以配置。

## 4. 流程

```
① 读材料 ─► ② 合成蓝图 ─►【确认蓝图】─► ③ 清点素材 ─►【缺素材提醒】
   (draft-analyst ∥ code-analyst)                              │
                                                              ▼
⑥ 自查与修改 ◄─ ⑤ 出图 ◄─【选质感】◄─ ④ 找参考 + 知识库检索
   │                                   (reference-scout ∥ figure-card-writer)
   ▼
【交付：并排对比 + 修改清单，用户最后确认】 ─► ⑦ 新图卡入库
```

用户确认点 **[用户决定]**：确认蓝图、缺素材提醒、选质感、交付前看对比图。除此以外全自动，不额外停下。参考论文列表**不**单独停下确认，但会写在交付报告里。

### ① 读材料（两个 subagent 并行）
- **draft-analyst**：从 draft 中提取方法的组成部分、数据流和训练/推理的区别、损失项、新模块的名字（全名 + 缩写，按作者写法原样保留）、作者认为的贡献点，以及 draft 里已有的图注和图引用。每一条都记录出处（章节和行号）。
- **code-analyst**：从代码中提取模型的类结构、forward 中的实际数据流、模块之间的调用关系、配置开关（比如训练和推理走不同分支）。每一条都记录出处（`file:line`）。它同时负责找出**能产出图用素材的脚本**（推理 demo、可视化脚本、样例数据），供第 ③ 步使用。
- 两者各自输出一份结构化报告，由编排者合并。

### ② 合成蓝图 →【确认蓝图】
- 编排者把两份报告合成一份蓝图（第 5 节），并标出**对账差异**：draft 写了但代码里没有的、代码里有但 draft 没写的、命名不一致的。
- 先给用户看：画哪些模块、怎么连、哪些是新模块及其名字、对账差异怎么处理。用户可以增删和改名。这一步之后不再改动内容结构。

### ③ 清点素材 →【缺素材提醒】 **[用户决定]**
- 列出蓝图中所有需要实物素材的位置，比如输入输出样例图、注意力图、中间结果、数据样本。
- 来源优先级：**运行项目代码得到** > 仓库里已有的图片和样例 > 请用户提供 > AI 生成（仅限装饰性插画，见第 9 节，**绝不**用 AI 生成冒充实验结果的图）。
- 运行代码：轻量命令（不训练、不下载大权重、不用 GPU 长跑）可以直接运行。重的命令只列出来，请用户确认后再跑，或者由用户自己跑好后给出路径 **[我的决定]**。
- 拿不到的素材整理成一张清单，**及时**告诉用户：要什么、放在图的哪里、建议的规格。用户暂时给不了的，先放**醒目标注**的占位框继续推进，交付报告里逐条列出未替换的占位。

### ④ 找参考 + 知识库检索（与 ③ 可并行）
- **reference-scout**（网络搜索 agent）：根据蓝图的领域、方法类型和目标会议，从相关顶会中找 **5–10 篇** **[用户决定]** 方法相近的论文。
  - 来源 **[我的决定]**：arXiv API、OpenReview API、CVF Open Access、ACL Anthology、Semantic Scholar API，都是免费接口。需要付费数据源时按用户的全局规则先询问。
  - 选文标准：同领域、目标会议及同档会议、近 2–3 年优先、方法结构相似（比如同样是"编码器 + 插入式模块"或"两阶段训练"）。
  - 下载 PDF，抠出方法图（`pdfimages` / `pdftoppm`，再按 "Figure N" 图注定位裁剪），放进**本地缓存**（不进 skill 目录，见第 6.3 节）。
- **figure-card-writer**：逐张看图，写成**图卡**（第 6.2 节）。
- 编排者再从知识库中取出对应会议的格式要求、领域卷的惯例和配色候选，连同这 5–10 张图卡一起汇总成一份**设计简报**（布局模式、信息流方向、配色候选、元素用法、新模块常见的标注方式）。

### 选质感 **[用户决定：做成正式环节]**
- 用**用户自己的蓝图内容**，在 2–4 种质感下各渲染一张小样，并排展示给用户。
- 质感 = 几个可以独立组合的维度 **[我的决定]**：配色方案 × 形状语言（直角/圆角/胶囊）× 立体效果（扁平/立方体特征图/阴影渐变）× 字体排印。所以用户可以说"B 的配色 + C 的立体特征图"。
- 候选来自知识库的质感卷，并由设计简报推荐（比如 CV 方向优先给出立体特征图的选项）。
- 展示方式 **[留给实现者]**：本地 HTML 页面或一张拼图 PNG，二选一即可，关键是能并排看清楚。
- **[我的决定]** 小样走的是和正式图同一条编译路径，并且必须先通过第 ⑥ 步的机械检查（不重叠、文字不溢出）才能拿给用户看。粗糙的小样也会影响用户对质感的判断。

### ⑤ 出图
- **[我的决定]** 采用 **"蓝图 + 质感配方 → 编译成 drawio XML"** 的方式，而不是让模型一次性直接手写整份 XML：
  - 布局由一个**布局步骤**决定：模型参考设计简报，给出网格化的布局，包括分组、行列、对齐关系和走线方向；
  - 再由**确定性脚本**把蓝图、布局和质感配方编译成 drawio 的 mxGraph XML，套用统一的样式：描边粗细、圆角、字号层级、间距、连线样式（正交走线和拐角）；
  - 这样每次产出可重复，后续可以机械检查，用户在 drawio 里改起来也规整。
- 新模块按蓝图的 `proposed` 标记，用质感配方规定的方式突出（容器色块、名字和缩写），名字必须原样出现 **[用户决定]**。
- 用 draw.io 桌面版命令行导出 PNG 和 PDF（本机已安装 `/Applications/draw.io.app`）。

### ⑥ 自查与修改
自查分两层，**两层都要过** **[我的决定]**。

**机械检查**（脚本读取 drawio XML 和蓝图）：
- 蓝图里的每个节点和每条边都在图里，图里也没有蓝图之外的节点和边（这项检查覆盖"主要组件都在"和"走线正确"）；
- 每个新模块的名字字符串都出现在它自己的节点或容器上；
- 元素之间没有意外重叠，文字没有溢出框外，连线没有穿过不相关的框；
- 按目标打印宽度换算后的最小字号不低于格式卷中该会议的要求；
- 疏密：同级元素的间距是否均匀、留白占比是否落在合理区间。**阈值用图卡库和验收集里真实论文图的测量值来校准，不靠拍脑袋**；
- 配色：色盲模拟和灰度下，相邻的不同类元素仍然能区分开；
- PNG 和 drawio 一致（由同一份 XML 导出，并核对时间戳和尺寸）。

**看图检查**（critic subagent 看真实渲染出来的 PNG）：
- 按五项评判：忠实于蓝图、简洁、易读、美观/质感、新模块是否突出且名字清楚（前四项借鉴 PaperBanana 的评测维度）；
- 和设计简报里的参考图对比，看风格是否到位；
- 输出具体的修改意见，例如"Decoder 左侧间距是右侧的两倍""跳连线和主干线交叉"，而不是笼统的"可以更好"。

**修改循环**：按意见修改后重新出图并复查。最多循环几轮 **[留给实现者]**（建议 3 轮）。到上限仍有没解决的问题时，**如实写进交付报告**，不能报告成"已通过"。

### 交付 →【用户最后确认】 **[用户决定]**
- 交付物：drawio、PNG、PDF；初稿和终稿的**并排对比图**；修改清单；没解决的问题和未替换的占位（如果有）；本次用到的参考论文列表（带链接）。
- 用户提出修改后，回到 ⑤ 或 ⑥。

### ⑦ 入库
- 本次新写的参考图卡并入图卡库（去重），见第 6.4 节。

## 5. 蓝图（中间产物）

蓝图是整个流程的核心契约：出图、自查和用户确认都以它为准。字段如下（具体 schema 和取名**[留给实现者]**）：

- `figure`：类型（overview / teaser / module-detail）、目标会议、目标宽度、信息流主方向、图中标签的语言（**[我的决定]** 默认英文，可配置）。
- `nodes[]`：`id`、`label`（图上显示的文字）、`full_name` / `abbrev`、`role`（`proposed` 新模块 / `reused` 已有组件 / `io` / `data` / `loss` / `annotation`）、`visual`（box / cuboid 特征图 / token 序列 / 图片素材 / 图标 / 公式）、`group`、`asset`（素材引用及其状态：已有 / 运行得到 / 待用户提供 / 占位）、`provenance`（draft 位置和/或 `file:line`）。
- `edges[]`：`src`、`dst`、`kind`（数据流 / 跳连 / 梯度或损失 / 训练专用 / 推理专用）、`label`、`provenance`。
- `groups[]`：阶段和子模块容器，比如 "Stage 1"、CSFM 容器。
- `discrepancies[]`：draft 和代码的对账差异，以及用户的处理决定。
- `layout`：第 ⑤ 步写入的网格布局。
- `style`：选定的质感配方 id 和组合参数。

## 6. 知识库

**建库方式** **[用户决定]**：先做一次系统调研建好一个大库，之后在使用中越用越多。

### 6.1 分卷 **[我的决定，用户已认可方向]**
| 卷 | 内容 | 来源要求 |
|---|---|---|
| 格式卷 | 各会议和期刊的栏宽、页宽、最小字号、图片格式要求 | 官方作者模板或投稿指南，每条注明链接和年份 |
| 配色卷 | 成体系的学术配色（如 Okabe-Ito、Paul Tol、ColorBrewer 等）的色值和适用场景；从真实论文图里采样到的配色 | 体系配色取自官方来源；采样配色关联到图卡 |
| 字体与排版卷 | 字体选择、字号层级、间距和疏密规则 | 数值来自对真实图的测量（关联图卡）或有出处的设计规范；没有数值依据的写成定性描述 |
| 质感卷 | 质感配方：配色 × 形状 × 立体效果 × 字体的参数组合，每种附一张示例渲染图；首批至少包括讨论中的 B（柔和浅色）、C（立体特征图）、D（极简编辑风），A（drawio 默认）只作对照 | 每个配方链接到体现该风格的图卡 |
| 领域卷 | 各方向惯用的视觉元素和画法（例：LLM 的 token 序列、CV 的立体特征图、RL 的 agent–环境循环、扩散模型的加噪去噪链、医学影像的 k-space） | 每条惯例至少链接到若干张图卡作为证据 |
| 图卡库 | 每张真实论文方法图一张卡片 | 见 6.2 |

### 6.2 图卡（每张参考图一条）
字段：论文标题、链接、会议、年份、领域、图的类型、布局模式（线性 pipeline / U 形 / 多分支 / 上下两阶段 / 左右对比 ……）、信息流方向、分组方式、色值采样（几个主色的 hex）、形状和立体效果、用到的元素（缩略图 / 图标 / 公式 / 特征图）、新模块怎么命名和突出、疏密的测量值（**[留给实现者]** 测量方法，比如框检测后统计间距和留白）、一句话"值得学的地方"。

### 6.3 版权与公开发布 **[用户决定：会公开发布]**
- skill 仓库里**只存文字图卡、色值、测量值和链接**，**不存**别人论文的原图或裁剪图。
- 运行时下载的参考 PDF 和抠出的图只放在**本地缓存目录**（**[留给实现者]**，如 `~/.cache/paper-figure/`），不进仓库，也不进交付物。
- 质感卷的示例渲染图由本 skill 自己绘制，内容使用虚构的示例方法。

### 6.4 首批建库与增长
- 首批调研作为一个独立的**建库模式**（`build-kb`）来跑，可以重复运行、增量补充。
- 首批规模 **[我的决定，可调]**：约 12 个领域，每个领域 20–30 张图卡，覆盖第 2 节所列的方向和第 6.5 节的会议，合计约 250–350 张。可以利用公开基准（SciFig-Bench、PaperBananaBench、FigureBench）的论文列表作为抽样来源，前提是它们的许可允许这样用 **[留给实现者核实]**。
- 增长：每次使用时，新写的参考图卡自动入库（按论文链接去重）；领域卷和质感卷**不**自动改写，由建库模式定期根据图卡重新归纳。这样核心卷保持稳定，图卡库持续增长。
- 存放位置 **[我的决定]**：随 skill 发布的知识库是**只读**的，放在仓库里。使用过程中新增的图卡写到用户本地的数据目录（具体路径**[留给实现者]**，如 `~/.local/share/paper-figure/`），读取时两层合并。这样每次使用都不会弄脏仓库。用户的图卡只有在维护者显式运行合并命令时才进入仓库。
- 每条内容都带 `source` 字段；没有出处的条目，建库脚本直接拒收。

## 7. Agent 一览

| Agent | 职责 | 并行关系 |
|---|---|---|
| draft-analyst | 读 draft，生成结构化报告 | 和 code-analyst 并行 |
| code-analyst | 读代码，生成结构化报告，并找出能产出素材的脚本 | 和 draft-analyst 并行 |
| reference-scout | 搜索并下载 5–10 篇参考论文，抠出方法图 | 和素材清点并行 |
| figure-card-writer | 看图写图卡 | 可按图分片并行 |
| critic | 第 ⑥ 步的看图检查 | 和 designer 分开，不共享上下文，保证独立 |
| 编排者（skill 本身） | 合成蓝图、和用户对话、布局、编译出图、驱动修改循环、交付 | — |

是否需要单独的 designer/layout agent，还是由编排者自己做布局：**[留给实现者]**。

## 8. 约束

- **不编造**：知识库、图卡和交付报告中不出现没有出处的数字、规律或引用。图中的模块和连线都要有 provenance。
- **花费**：图像和 LLM 生成默认走 codex 订阅。任何付费 API 或付费数据源都要先征得用户同意。
- **依赖**：draw.io 桌面版命令行（导出用）、poppler（`pdfimages`/`pdftoppm`）、Python。官方 `drawio-mcp` 可以作为可选的"在编辑器中打开"通道，但不能是必需依赖 **[我的决定]**。
- **平台**：先保证 macOS 可用；准备公开发布，路径和依赖检测要通用，不能写死本机路径。
- **git**：本地提交，**不 push**，直到用户在某次请求里明确说要发布。

## 9. 图标与插画 **[用户决定：矢量为主，AI 生成兜底]**
- 首选：许可允许再分发的开源矢量图标库（具体用哪些库、许可是否兼容，**[留给实现者核实]**），以及 drawio 自带的图形。图标统一描边粗细和配色，跟随质感配方。
- 兜底：确实需要插画时（多见于 teaser），用 codex 订阅生成位图，放进 drawio 作为图片元素，交付报告里注明"此处为 AI 生成，不可编辑"。
- 禁止：用 AI 生成的图冒充实验结果、数据样本或模型输出。

## 10. 验收 **[用户决定：两者都用]**

- **固定基准集**：选若干篇（**[我的决定]** 首批 6–8 篇，覆盖不同领域和三类图）已发表、有开源代码的论文。只给 skill 方法部分的文字和代码，**不给原图**，让它画图，再把产出和原论文的图**并排**放给用户评判。基准集和每一版的结果都存档，之后每次改进 skill 都在同一套题目上对比，**只有不比上一版差才保留改动**。
- **实战检验**：用户自己的论文由用户主动提供，不去扫描用户的文件。
- 首次交付时，就把基准集上的第一版结果存成**基线**。每个分期（第 14 节）各记录一次基线，因为知识库扩充后，旧基线就不可比了。
- **谁判定"不比上一版差"** **[我的决定]**：每次改动后，先由自动评审在固定基准集上对新旧两版做**盲评**（随机左右顺序，按第 ⑥ 步的五项打分），作为保留或回退的门槛。到每个里程碑时，把"上一版 vs 这一版"的**并排对比图**交给用户评判，用户的判断优先于自动评审。

## 11. 已定决定汇总（用户在讨论中明确的）
1. 输入为 draft 和/或代码，两者都有最好，各由一个 subagent 分析。
2. 新模块的名字要原样出现在图中。
3. 选质感是正式环节；B（柔和浅色）和 C（立体特征图）是用户中意的方向。
4. 素材优先运行项目代码得到，缺的要及时提醒用户提供。
5. 只画示意类图：方法总览、teaser、模块细节；不画数据图表。
6. 覆盖各个 AI 方向。
7. 知识库先建一大库，再越用越多；准备公开发布，所以不存原图。
8. 图标以矢量为主，AI 生成兜底。
9. 用户确认点：确认蓝图、缺素材提醒、选质感、交付前看对比图。
10. 验收用公开论文基准集加用户自己的论文。
11. 输出 drawio 和 PNG；参考论文每次 5–10 篇。
12. 名字和位置：`paper-figure`，`~/code_project/paper-figure`。
13. teaser 指概念对比示意，不做结果拼图。
14. 旧 `paper-figures` 时期的个人画图偏好不再适用；旧 skill 是因为出图质量不行而删掉的。

## 12. 留给实现者
蓝图 schema 的具体字段名；布局算法（模型给网格、脚本细排，或者其他方案）；疏密测量方法和阈值校准流程；修改循环的轮数上限；选质感的展示形式；输出目录的默认值；本地缓存路径；图标库的选择和许可核实；建库模式的抽样脚本；基准集的具体篇目（需和用户确认领域分布）；是否单设 designer agent。

## 13. 相关工作与借鉴点
- **PaperBanana**（Google + 北大，ICML 2026，arXiv 2601.23265）：Retriever → Planner → Stylist → Visualizer → Critic 五个 agent，生成后迭代自查。借鉴：单独设风格角色，从参考图中提炼风格；自查的四个评测维度；以 NeurIPS 2025 方法图为测试题的思路。不同点：它输出不可编辑的位图。
- **AutoFigure / AutoFigure-Edit**（ICLR 2026 / ACL 2026 demo，github.com/ResearAI/AutoFigure、AutoFigure-Edit）：先把文字转成结构化蓝图，验证布局后再渲染；Edit 版输出可编辑的 SVG。借鉴：蓝图作为中间契约。附带 FigureBench（3,300 对文本和图）。
- **SciFig**（arXiv 2601.04390）：SciFig-Bench 收录 435 张人工核验的方法图，覆盖 37 个 AI/ML 领域和 15 个顶会，可作为图卡抽样来源。
- **drawio-academic-skills**（bahayonghang/drawio-skills）：开画前声明会议、图类型和配色策略；导出前检查灰度和字号。可参考它的检查清单。
- **jgraph/drawio-mcp**：draw.io 官方 MCP 和 Claude Code 插件，可作为可选的"在编辑器中打开"通道。
- **K-Dense scientific-schematics**：用 Nano Banana 生成位图示意图，不可编辑，是我们不走的路线。

## 14. 分期 **[我的决定]**

旧 skill 败在出图质量上，所以按"先证明质量，再铺开"的顺序分期：

- **第 0 期：质量验证。** 从基准集里挑 2 篇论文，手工写好它们的蓝图，只做"蓝图 + 质感配方 → drawio → PNG"这一段，包括 B、C 两种质感和机械检查。把产出和原论文的图并排给用户看。**这一期用户认可了，才进入第 1 期**；认可不了就先改编译器和配方，不铺功能。
  - 已验证的可行性：用本机 draw.io 导出测试过，立体特征图（`shape=cube`）、渐变和阴影都是 drawio 原生能力，导出后仍可编辑（见 `docs/mockups/cube.drawio`、`cube.png`）。待修正：立方体的侧面朝向和讨论时的样例相反，需要调整参数。
- **第 1 期：完整流程 + 种子知识库。** 实现第 4 节的全部步骤和确认点。知识库中，格式、配色、字体与排版、质感四卷一次建全；图卡和领域卷先只覆盖基准集涉及的领域。在基准集上记录第 1 期基线。
- **第 2 期：全量建库。** 运行建库模式，完成第 6.4 节的首批规模（约 250–350 张图卡）和全部领域卷，然后重新记录基线。

讨论时用的质感样例（A/B/C/D）保存在 `docs/mockups/texture-options.html` 和 `.png`。内容是虚构的示例方法，可以作为质感卷的起点。
